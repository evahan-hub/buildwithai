9 jobs × 43 sub-steps → one 46-row Converged Journey. A single dataset that carries both lenses, with every field traceable to its source.

Zoom in 2: From a one-pager doc to a full journey prototype
1Problem to solve

The device experience in the Customer Area was 10+ disconnected table menus, with no shared model and everything edited one device at a time. And the vision doc was still abstract about how it actually helps users, so it didn't turn itself into a buildable flow.

2Result

10+ menus → three Customer-Area products, as one clickable North Star prototype. Device Intelligence (fleet dashboard + NL search), Devices & Locations (stores/devices, reassign, order) and Device Studio (config wizard + live preview).

The process: Vision doc→ Scoped PRD brief→ 3 products (from 10+ menus)→ Clickable prototype
↳ How to build the flow from the doc: JTBD journey→ Component framework→ Details per component→ Connect each journey
3The decisions

A few decisions did the heavy lifting. Lock these and the model structures around them instead of inventing the product:

Shape the products from JTBD

An intuitive call, grounded in the JTBD and how the area is used today. That became the three products, each with a one-line "what it solves."

Focus on the current journey

Stay on the journey merchants have today and improve it from user insights, rather than trying to cover everything at once.

Describe the behaviour concretely

Spell out how each part actually behaves: natural-language search, all-stores / all-devices views, reassign, a control panel with a live simulator.

Layer in realistic data over time

It needn't be precise at first, but realistic figures and stats (143 settings across 26 groups, 656k active vs 419k trading) make it land for the viewer.

Feed it good examples

Point at benchmarks and existing UIs like the DCC report, Looker, and Square / Stripe, so solutions anchor to patterns people already know.

Prompts  ·  hard-won lessons

What I learned the hard way

It invents numbers with total confidence. I caught a "900" that never existed, so now I make it cite a source or say "I don't know."
It quietly skips sources. I had to ask "did you actually use the NPS file? the Slack Q&A?", so always check coverage.
It can't always read what it claims. Inline files weren't really parsed, just approximated, so confirm it used your real source.
It guesses the merge when tables don't match. Different taxonomies → it invents a mapping. Lock the approach before it builds.
It jumps to screens too early. Ask for a PRD and it starts drawing pages. Settle the JTBD journey and component framework first, or the flow won't connect.
